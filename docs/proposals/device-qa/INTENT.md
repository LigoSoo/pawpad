# device-qa 스킬 — 만든 의도와 근거

> 출처: TodayQuest 프로젝트(Flutter/Android) 2026-09-02~03 세션. 스킬 원본은 이 폴더의 `SKILL.md`.
> 이 문서는 "왜 만들었나"를 담는다. 툴킷에 녹일 때의 작업 지시는 `INTEGRATION_PROMPT.md`.

## 1. 사건 (측정된 사실)

실기기(Galaxy Note 8, Android 9)에 앱을 깔고 QA를 돌렸다. 방식은 흔한 UI 자동화 루프였다:

```
screencap → 이미지 read → 좌표 계산 → adb input tap → screencap → 이미지 read → …
```

- 생성된 스크린샷 **98장**(21MB), 그중 **약 50장을 컨텍스트로 read**
- 결과: **5시간 사용 한도가 그 세션에서 소진**됨. 사용자가 이상을 감지하고 테스트 기기를 분리
- 같은 세션의 코드 수정·테스트·빌드(analyze/test 941건/APK 2회)는 비용에서 미미했다

## 2. 왜 그렇게 비싼가 (메커니즘)

스크린샷 1장이 텍스트 수천 자에 맞먹는 것은 절반의 이유다. **지배적인 항은 재전송이다.**

- 에이전트는 도구를 호출할 때마다 **그때까지의 대화 전체**를 다시 보낸다
- 따라서 읽은 이미지 1장은 그 뒤의 모든 호출에 계속 실려 나간다
- 비용 ≈ `이미지 수 × 이후 호출 수` → **루프를 돌릴수록 제곱꼴로 증가**

QA는 본질적으로 도구 호출이 많은 작업(탭·스와이프·대기·판독)이라 이 곱셈이 가장 크게 터지는 자리다.

## 3. 위임(delegate)은 해법이 아니다 — 이 판단이 이 스킬의 핵심

처음 나온 제안은 "`code-delegate`처럼 `qa-delegate`를 만들어 서브에이전트에 넘기자"였다. 검토 결과 **거절**했다:

- 서브에이전트는 독립 컨텍스트라 **부모는 깨끗해진다**. 하지만 같은 이미지 루프가 **서브 안에서 그대로 탄다**
- 사용량 한도는 부모/자식을 구분하지 않는다 → **비용이 안 보이는 곳으로 숨을 뿐, 다시 소진된다**
- `code-delegate`가 잘 작동한 이유는 위임 자체가 아니라 **넘길 설계가 이미 문서로 있어 주고받는 양이 작았기** 때문이다. QA는 정반대다 — 본질이 "화면을 계속 들여다보는 것"이라 위임해도 그 양이 안 줄어든다

→ 그래서 이 스킬은 **위임 스킬이 아니라 검증 프로토콜 스킬**이다. 위임은 "프로토콜을 지킨 뒤에만 의미 있는 선택 모드"로 격하하고, 그 한계를 스킬 본문에 명시했다.

## 4. 진짜 지렛대 — 화면을 이미지로 읽지 않는다

그 세션에서 내가 눈으로 확인한 값들을 다시 보면 대부분 **글자**였다:

`2/4단계` · `구구단 2·3·4단` · `초1 수준은 고른 연산에 없어서…` · `코드를 찾을 수 없어요` · `9/10` · `2 / 10 퀘스트`

전부 `uiautomator dump`의 텍스트 노드로 잡힌다. 그리고 결정적으로 **bash에서 grep으로 걸러 낸 뒤 결과 줄만 컨텍스트에 들인다**:

```sh
grep -q "2/4단계" /tmp/ui.xml && echo PASS      # 수십 토큰
```

스크린샷 1장(수천 토큰 + 이후 전 호출 재전송)과 자릿수가 다르다.

부수 효과가 하나 더 있다 — **정확도가 올라간다.**
- 탭 좌표를 눈대중이 아니라 노드의 `bounds`에서 계산한다
- "FAB이 마지막 항목 삭제 버튼을 가리는가" 같은 겹침 판정은 두 `bounds` 사각형의 교차 계산이 사람 눈보다 엄밀하다
- 진동 검증은 이미 이 방식이었다(`dumpsys vibrator`의 `Previous vibrations`에서 `OneShot{mDuration=40}` 확인) — 그 세션에서 **가장 싸고 가장 확실한 검증**이 로그 기반이었다는 게 방향을 증명한다

## 5. 스킬의 구조 (설계 결정)

| 결정 | 내용 | 이유 |
|---|---|---|
| 검증 채널 우선순위 | `uiautomator dump` > `dumpsys`/`logcat` > 앱 DB > 스크린샷 | 위 3개로 판정 가능한 것을 이미지로 하지 않는다 |
| 어서션 먼저 | 화면 보기 전에 기대 문자열/조건 목록 작성 | QA가 "목록 채우기"가 되어 탐색적 화면 순회가 줄어든다 |
| 스크린샷 예산제 | 세션당 8장 + 사유 기록 + 종료 시 삭제 | 상한이 없으면 "한 장만 더"가 반복된다. 글자로 환원 안 되는 것(잘림·색·처음 보는 화면 구조)에만 허용 |
| 안전 가드 | 블라인드 연속 탭 금지 · 탭 금지 라벨(`계정 삭제`·`데이터 초기화`·`로그아웃`…) · 파괴적 조작 사전 확인 · 화면 꺼짐 확인 | 과거에 블라인드 탭으로 계정 삭제 다이얼로그를 건드린 사고가 있었고, 이번 세션에도 **화면이 꺼진 채 쏜 탭이 통째로 유실**되는 일이 두 번 있었다(그 사이 만든 QA 데이터가 절반만 생성됨) |
| 위임은 선택 모드 | 반환은 `PASS/FAIL + 근거 1줄`, XML·스크린샷 반환 금지 | 위임의 유일한 실익(부모 컨텍스트 보호)만 취하고 착시(총량 절감)를 차단 |
| 산출물 고정 | lane `Verification Evidence`에 바로 붙는 블록 형식 | PawPad DoD 7번과 직결 |

## 6. 정직하게 남긴 미검증 항목

- **`uiautomator dump`를 그 노트8에서 실증하지 못했다.** 스킬을 쓰기로 결정한 시점에 기기가 이미 분리된 뒤였다. 그래서 스킬 본문에 "첫 사용 시 1회 검증, 실패하면 그 화면만 스크린샷 + 사유 기록"을 넣어 뒀다. 툴킷에 넣기 전에 아무 안드로이드 기기에서 한 번 돌려 보면 좋다
- 기기·앱에 따라 dump가 빈 계층을 내거나 애니메이션 중 실패하는 사례가 알려져 있다 → 폴백 경로를 스킬에 이미 명시

## 7. 툴킷에 넣을 때 판단이 필요한 지점

이 스킬은 **Android/adb 전제**다. 다른 스킬들과 성격이 다르다:

- `adb`·`uiautomator`·`dumpsys`는 안드로이드 전용. iOS·웹·데스크톱에는 그대로 안 맞는다
- 다만 **원리(텍스트 우선 · 어서션 먼저 · 스크린샷 예산 · 결과만 컨텍스트에)는 플랫폼 무관**하다.
  iOS는 `xcrun simctl` + accessibility, 웹은 DOM 텍스트/셀렉터, 데스크톱은 접근성 트리로 같은 구조가 성립한다

→ 그래서 툴킷 편입 방식은 두 갈래다(선택은 툴킷 소유자 몫):

1. **stack/bundle 게이트로 그대로 편입** — 새 번들 `qa`(또는 mobile stack 조건)로 설치 대상을 한정. 지금 문서 그대로 쓸 수 있다. 가장 빠르다
2. **일반화 후 편입** — 스킬 본문을 "채널 우선순위 + 예산 + 가드"의 플랫폼 중립 골격으로 올리고, adb 명령 모음은 `references/android.md`로 분리(`design` 스킬의 `references/` 선례). 확장성은 좋지만 작업량이 는다

내 권고는 **1번으로 먼저 넣고**, iOS·웹 QA 수요가 실제로 생기면 그때 2번으로 승격하는 것이다. 지금 일반화하면 검증된 사례가 안드로이드 하나뿐이라 추측으로 골격을 짜게 된다.

## 8. 이 스킬이 대체하는 습관

기존에는 기기 QA에 대한 규칙이 프로젝트 메모리와 lane 관행에만 흩어져 있었다(콜드 스타트, 타임존 정렬, `flutter build apk --debug` 명시, DB 직접 편집, 에뮬 진동 관측 불가 등). 이 스킬은 그것들을 **실행 순서가 있는 하나의 절차**로 묶고, 가장 비싼 실수(스크린샷 루프)에 상한을 건다.
